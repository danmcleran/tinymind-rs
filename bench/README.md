# On-board checks

Functionality and performance of the `tinymind` crate on two boards, mirroring
tinymind (C++)'s [framework comparison](https://github.com/danmcleran/tinymind/tree/master/benchmarks/framework_comparison_f411):
same boards, clocks, flash wait states, timing method, model weights and test
samples, so the numbers sit next to the tinymind (C++) ones.

| Board | Core | Clock | Timing |
|---|---|---|---|
| NUCLEO-F411RE | Cortex-M4F | 100 MHz, 3 wait states, ART on | DWT cycle counter |
| NUCLEO-L031K6 | Cortex-M0+ (no DSP, no hardware divide) | 32 MHz, 1 wait state, prefetch on | SysTick with wrap interrupt (no DWT on M0+) |

`src/board.rs` is a register-level port of tinymind (C++)'s `board/board.cpp` and
`board/board_l031k6.cpp`. Cycle counts are the median of 33 warm runs.

## Workloads

- **`mlp`**: tinymind (C++)'s int8 digits MLP (64-32-16-10, per-channel requantizers,
  ReLU fused into the requantizer) on `QDensePerChannel`, generated by `gen.py`
  from tinymind (C++)'s benchmark headers: the same int8 weights, requantizers and test
  samples (360 on the F411, the first 32 on the L031, as tinymind (C++) uses). The
  output hash over every sample must equal tinymind (C++)'s expected hash, which
  tinymind (C++) and TFLM both produce on these boards.
- **`xor-q16`, `xor-q8`**: tinymind (C++)'s xor example trained on the board, 20,000
  steps in Q16.16 and in Q8.8. The device hashes the exact bytes of the
  `nn_fixed_xor.txt` the example writes (every weight after every step) and
  compares with the golden hash in `tests/xor_golden.rs`.
- **`anomaly`**: the anomaly-detection demo (`examples/common/anomaly_demo.rs`,
  shared with `examples/anomaly.rs`): an 8-4-8 Q16.16 autoencoder trains on 3,000
  synthetic normal windows on the device, sets its threshold and screens 512 test
  windows. The report must equal the host's, and its hash (every trained weight
  and every score) must equal `EXPECT_HASH` in `src/anomaly.rs`, which the host
  run and `tests/anomaly_golden.rs` pin. No C++ counterpart.
- **`fft`**: one 256-point forward transform of `int8::QFft1D` and the
  squared magnitudes of its bins, on the FFT sweep's random signal with
  tinymind (C++)'s twiddle tables (`build.rs` reads both, and the hash
  tinymind (C++) printed for that transform, from
  `tests/golden/fft/stdout.txt`). The spectrum's hash must equal the one
  tinymind (C++) printed. `fft-runtime` is the same with the layer built at
  run time from tables the compiler cannot see, instead of a `static`.
- **`trees`**: the two imported scikit-learn models of the `imported_trees`
  example (gradient boosting, 90 trees on int8 inputs; random forest, 15
  voting trees on int16) classify the 54 held-out UCI Wine samples; the hash of
  every raw output and class must equal the host's (`EXPECT_HASH` in
  `src/trees.rs`). Both forms are timed, and the pool walk is timed from flash
  and from a copy in SRAM. The L031 image is built at `opt-level = "s"` to fit.
- **`kws`**: tinymind (C++)'s KWS-shaped int8 CNN from its framework comparison
  (20x20x1 input, conv 3x3x8 and pointwise layers with per-channel
  requantizers, 2x2 max pool, 3x3 depthwise, global average pool, a 16-10 dense
  head; random weights and inputs), generated by `gen.py` from tinymind (C++)'s
  benchmark headers. The output hash over its 8 test inputs must equal
  tinymind (C++)'s, which TFLM also produces. **`kws-profile`**: the same with
  per-layer timing.
- **`mlperf-kws`** (F411 only): the MLPerf Tiny keyword-spotting reference model
  (DS-CNN, 49x10 MFCC input, 12 classes), translated from its `.tflite` by
  `tools/import_tflite`. Generate it first with `python3 -I
  tools/import_tflite/mlperf.py kws --out bench/src/gen/mlperf_kws.rs --data
  bench/src/gen/mlperf_kws_data.rs` (a Python with `tflite`; the model is
  downloaded, Apache-2.0, not committed), then `WORKLOADS="mlperf-kws"
  bench/run.sh f411`. Its output hash over 8 seeded random inputs must equal
  tinymind (C++)'s, which TFLite's reference kernels also produce.
- **`mlperf-ic`** (F411 only): the MLPerf Tiny image-classification reference
  model (ResNet-8, 32x32x3 input, 10 classes, three residual blocks), the same
  way: `mlperf.py ic --out bench/src/gen/mlperf_ic.rs --data
  bench/src/gen/mlperf_ic_data.rs`, then `WORKLOADS="mlperf-ic" bench/run.sh
  f411`.
- **baseline** (no workload feature): the MLP harness with a do-nothing network,
  for size and stack deltas. **`profile`**: the MLP with per-layer timing.

## Results

Every Rust figure was measured 2026-11-11 on both boards, with the build
settings below. Rust 1.99.1. C++ figures are tinymind (C++)'s own
(`docs/benchmarks.md`, gcc 13.2.1 `-O3`), measured on these same boards.

### Build settings

The Rust images are built with the settings of tinymind (C++)'s benchmark
Makefile (`benchmarks/framework_comparison_f411/Makefile`), so a difference in
cycles comes from the code, not from the compiler options. Keep them matched:
when the C++ build changes a setting, change it here and re-run both boards.

| | tinymind (C++), gcc | tinymind-rs, rustc | Where |
|---|---|---|---|
| Optimisation | `-O3` | `opt-level = 3` | `Cargo.toml` |
| Core | `-mcpu=cortex-m4` / `-mcpu=cortex-m0plus` | `-C target-cpu=cortex-m4` / `cortex-m0plus` | `.cargo/config.toml` |
| Floating point | `-mfloat-abi=hard -mfpu=fpv4-sp-d16` / soft | the target triple | `run.sh` |
| Whole program | header-only templates: the model is one translation unit | `lto = true`, `codegen-units = 1` | `Cargo.toml` |
| Unused code | `-ffunction-sections -fdata-sections -Wl,--gc-sections` | the linker's default | |
| Exceptions / panics | `-fno-exceptions -fno-rtti` | `panic = "abort"` | `Cargo.toml` |
| Loop alignment (F411) | none | `-C llvm-args=-align-loops=16` | `.cargo/config.toml` |

Two exceptions. Loop alignment is Rust only, for stable timings (next
paragraph). The SMLAD rows add a setting on each side: tinymind (C++)'s +SMLAD
build `-DTINYMIND_ENABLE_SIMD_ARM_DSP=1`, the Rust parallel-DSP row `-C
llvm-args=-arm-parallel-dsp-load-limit=512`. The L031 trees image is built at
`opt-level = "s"` to fit, and the `opt-level = "s"` rows say so.

Before 2026-11-11 the Rust images were built without `target-cpu` (the target
triples alone tune for a generic core). Matching `-mcpu` changed the F411
figures both ways, measured the same day with each setting: MLPerf DS-CNN
13,225,965 -> 11,850,835 cycles (-10.4%), ResNet-8 64,407,536 -> 58,807,476
(-8.7%; with the parallel-DSP flag 41,401,469 -> 38,273,811), the MLP 21,502
-> 20,437 (-5.0%), gradient-boosting trees 1,841 -> 1,680 inline and 9,276 ->
8,828 as a pool walk; the KWS-shaped network 186,257 -> 189,097 (+1.5%, its
pointwise layer 37,789 -> 43,652), the 36-tree subset 3,549 -> 3,793 and the
anomaly demo's training step 6,437 -> 8,811 (+37%) and detection 1,332 ->
1,611. xor was within 1%. On the L031 the code changed (a few hundred bytes
more flash) but no timing moved by a cycle.

The anomaly slowdown comes from LLVM's machine scheduler, which
`target-cpu=cortex-m4` turns on. The demo's layers are small enough that LLVM
unrolls each neuron's weighted sum completely (8 inputs, 4 neurons), and the
scheduler then starts all eight 64-bit Q16.16 products before narrowing any
of them; the products no longer fit in the core's registers and go to the
stack (training-step stack frame 164 -> 580 bytes, stack loads 47 -> 226).
Adding `-C llvm-args=-enable-misched=false` brings the step back to 6,415
cycles and detection to 1,350, but costs the int8 MLP 9.7% (20,437 -> 22,428)
and the KWS-shaped network 4.0% (189,097 -> 196,624), so the images keep the
scheduler on, as the C++ build's settings do. A project dominated by small
Q16.16 layers can measure both settings. The spills are reported upstream as
[llvm/llvm-project#241851](https://github.com/llvm/llvm-project/issues/241851)
(cortex-m3, m4, m33 and m35p share the scheduling model). Scheduling top-down
instead (`-C llvm-args=-misched-prera-direction=topdown`) avoids most of them,
but it is no general fix either. On the F411 (2026-11-12, every hash matching)
the anomaly step took 6,518 cycles and detection 1,326, the KWS-shaped network
175,319 (-7.3%) and the trees 0.3-2.4% less, while the MLPerf DS-CNN took
11,875,413 (+10.1%), ResNet-8 59,614,538 (+1.4%) and the int8 MLP 20,835
(+1.9%). The L031 images were identical with and without it. The images keep
the default. After the dense layers' one-rounding loop (later that day) the
int8 MLP takes 19,149 cycles, 20,073 without `target-cpu` (+4.8%), 20,358
with the scheduler off (+6.3%) and 18,930 top-down (-1.1%).

F411 images are built with every loop aligned to 16 bytes (`-C
llvm-args=-align-loops=16`, in `bench/.cargo/config.toml`), so a timing does not
depend on where unrelated code changes move the hot loops. Without it, the same
workloads moved by up to 2% when all code was shifted by 4, 8 or 12 bytes, and a
library change that moved a loop by 10 bytes, with no other effect, made the
MLPerf DS-CNN 11% slower (17,882,704 cycles against 16,115,226); with it, every
timing is identical at every offset. The padding costs 0-2% on most workloads at
`opt-level = 3` (the tree walks the most: 2% from flash, 7.8% from SRAM, as
their short loops are entered once per tree), 12% on the KWS-shaped network at
`opt-level = "s"`, and up to 1.7 KB of flash. The L031 images are built without
it: its flash fetches 32-bit words, and its functions start on 4-byte
boundaries, so moving the code cannot be swept the same way; its figures stay
sensitive to placement (see below).

### Quantized FFT, 256 points

Forward transform, median cycles, prefetch on, same signal and twiddle tables
and the same output hash in both languages (2026-11-12):

| | F411 | L031 |
|---|---:|---:|
| **tinymind-rs**, `static` layer, `opt-level = 3` | **41,991** (420 us) | **91,430** (2.86 ms) |
| **tinymind-rs**, `static` layer, `opt-level = "s"` | **44,255** | **96,784** |
| tinymind-rs, layer built at run time (`fft-runtime`), `opt-level = 3` | 45,619 | 97,221 |
| tinymind-rs, layer built at run time, `opt-level = "s"` | 43,864 | 98,389 |
| tinymind (C++), gcc `-O3`, best measured | about 82,900 | about 101,600 |
| tinymind (C++), gcc `-Os`, best measured | about 85,200 | 142,482 |

On the L031 the Rust transform takes about 10% fewer cycles than the best
gcc `-O3` build of tinymind (C++) and 32% fewer than its best `-Os` build;
on the F411 about half the cycles of either. The squared magnitudes of the 256 bins take 2,731 and 4,863
cycles. Code for the transform (L031): 2,056 B at `"s"` and 3,808 B at 3; the
C++'s 392 B at `-Os` and 584 B at `-O3` plus its 1 KB bit-reversal table; both
also read the 512 B of twiddle tables. The workload as a whole adds 2,920 B
(`"s"`) and 5,052 B (3) of flash on the L031 over the baseline image, with
the signal generator and the report, and about 4 KB of stack for its own
buffers (the input kept for 33 timed runs, the working buffers, 1 KB of
magnitudes); the transform itself needs none.

The C++ figures come from tinymind (C++)'s benchmark harness (`fw/harness.cpp`,
its board code and Makefile flags) with backends that run
`QFFT1D<256>::forward` on the same signal and tables. **gcc's code for that
loop depends on the function it is inlined into**, so the same source
measured 101,600 to 193,277 cycles on the L031 at `-O3`:

| Caller of `forward` (L031, gcc `-O3`) | Butterfly loop | Cycles |
|---|---|---:|
| the harness's timed function, on global arrays | 184 B; 10 stack loads, 3 stores, 2 literal-pool loads per butterfly | 158,603-166,833 |
| a non-inlined function taking two `int16_t*` | | 193,277 |
| a non-inlined function taking a struct of the two arrays by reference | 170 B; 13 stack loads, 6 stores, 2 literal loads | 158,224 |
| a processing function that copies the input into such a struct, then calls `forward` | 138 B; 4 stack loads, no stores, no literal loads | 103,492 (1,861 of it the copy) |

The best rows above are that last caller with the copy subtracted (F411:
84,200 - 1,278; L031: 103,492 - 1,861), and at `-Os` on the L031 the
harness's own function with the object built at run time (in the processing
function: about 152,200). Loop alignment (`-falign-loops=8` or `16`) moved the
C++ by 3%; the language standard (`-std=c++14 -ffreestanding` or
`-std=c++17`), a `const` object against one built at run time, and the input
(random, a two-tone signal, a low-amplitude one) did not explain the spread.
First measured in the harness's own function, the C++ took 107,292 / 166,833
cycles at `-O3` and 113,125 / 143,245 at `-Os` (F411 / L031), and the
comparison here first said the Rust was 17-30% faster on the L031 at
`opt-level = 3`; against the best C++ caller it was 16% slower before the
saturation skip, and is now 10% faster. The rustc
transform is a function of its own at `opt-level = 3`, so its code does not
depend on the caller in the same way.

Where the Rust cycles went (L031, `static` layer, `opt-level = 3`): 172,685 as
first ported (group by group, as the C++); 153,698 running each stage twiddle
by twiddle (each twiddle loaded once per stage, not once per butterfly);
117,640 with each stage's half size a constant (one loop per stage, chosen by
a macro over the powers of two), so offsets, strides and trip counts are
immediates and the M0+'s eight low registers hold the butterfly; 91,430
skipping the saturation when both twiddle products fit in `i16` (then every
halved sum does: `top + t` lies in [-65536, 65534], `top - t` in [-65535,
65535]), one range check per butterfly instead of four saturations, each of
which loaded its bounds from the literal pool (at `"s"`: 135,233 -> 96,784).
All give the same bits: the butterflies of a stage are independent, and a
Kani proof shows the saturation skip changes no output for any samples and
twiddle. The skip is for cores without a saturating instruction: on the F411
it cost 15-34% (`ssat` saturates in one cycle), so it is chosen at compile
time by `cfg(not(target_has_atomic = "32"))`, the only `cfg` that tells
ARMv6-M from Armv7-M on stable Rust. Tried and dropped: saturating with `(v >> 15) + 1 <= 1` instead of a clamp (no faster on
the L031; the F411 lost `ssat`, 59,965 -> 85,251); real outputs before
imaginary ones (F411 4% faster, L031 4% slower); constant stages only for half
sizes 1-8 (same at 3, 141,374 at `"s"` for 764 B less flash). The bit reversal
(no table) takes about 9,300 cycles of the L031 total.

### KWS-shaped CNN (int8 convolutions)

Code + weights = image - baseline image - test inputs (3,200 B); RAM = static
data plus peak stack, each above the baseline's.

| | F411 (100 MHz) | L031 (32 MHz) |
|---|---:|---:|
| **tinymind-rs**, cycles | **189,097** (1.89 ms) | **649,286** (20.3 ms) |
| tinymind (C++) scalar, `-O3` | 254,766 | 740,279 |
| tinymind (C++) +SMLAD, `-O3` | 181,853 | – (no SMLAD on the M0+) |
| TFLM int8 (CMSIS-NN), `-O3` | 576,368 | does not fit in 32 KB |
| **tinymind-rs**, code + weights / RAM | **8,056 B / 4,420 B** | **8,352 B / 4,848 B** |
| tinymind (C++) scalar `-O3`, flash / RAM | 6,608 B / 5,308 B | 8,220 B / 5,596 B |
| tinymind-rs at `opt-level = "s"`, cycles / code + weights | 537,118 / 4,372 B | 1,171,205 / 4,120 B |

Per layer (cycles, each layer timed separately; C++ scalar `-O3` in brackets):

| Layer | F411 | L031 |
|---|---:|---:|
| conv 3x3, 8 filters | 98,406 (183,748) | 400,956 (510,808) |
| max pool 2x2 | 9,527 (10,158) | 20,192 (24,921) |
| depthwise 3x3 | 22,061 (20,668) | 69,218 (72,544) |
| pointwise 8 -> 16 | 43,652 (41,835) | 138,649 (135,798) |
| global average pool | 2,583 (2,282) | 4,704 (5,756) |
| dense 16 -> 10 | 1,601 (1,302) | 3,347 (2,696) |

- **Faster than the portable C++.** The Rust model takes 26% fewer cycles than
  tinymind (C++)'s portable build on the M4F and 12% fewer on the M0+, and is
  4.0% behind its SMLAD build on the M4F, without SIMD. It uses less RAM, 22%
  more flash on the M4F and 2% more on the M0+ than the C++ at `-O3`. At
  `opt-level = "s"` the network's code and weights take 4.1-4.4 KB, and it
  runs 1.8-2.8x slower. The figures in the next two points were measured
  before the build settings were matched to the C++ (2026-11-11).
- **Where it comes from.** The stem convolution (one input channel) gathers
  each window once, padding filled with the zero point, folds the zero point
  into each filter's bias and runs the filters in pairs, so each window value
  loaded serves two: 22-41% faster than the C++'s gathered patches. Pointwise
  runs filter by filter, two pixels at a time (each weight loaded serves both;
  four would spill registers), and depthwise channel by channel, as the C++
  does: the zero point folded into the bias, the weights held across the
  pixels and the requantizer prepared once per filter (tinymind (C++)'s `FastRequantizer`,
  extended to the ranges of a fused ReLU and proved equal to `apply` by Kani).
  A depthwise window that lies inside the input reads it as slices without
  per-tap checks. That took depthwise from 46,049 to 22,732 cycles and
  pointwise from 78,614 to 41,028 on the M4F (measured before loop alignment,
  as are the figures in the next point); two pixels per pass then took
  pointwise to 37,788 (and the MLPerf DS-CNN's 64-channel pointwise layers from
  2.60M to 2.17M cycles each), on the M0+ 1% slower (138,649).
- **Measured, not assumed.** Running the stem filter by filter as well made
  it 20% slower (135,172 cycles), so it reads each window once. The 16-bit
  path of the multi-channel convolutions is slower for a one-channel stem
  (286,132 cycles for the network). One pixel
  loop branching on the requantizer form per output, instead of one loop per
  form, saved 0.5 KB and cost depthwise 27%. Requantizers without a prepared
  form (a scale ratio of 0.25 or more) run a cold out-of-line loop: on this
  model they would cost depthwise 31% and pointwise 36%.
- **No buffer reuse needed.** The C++ ping-pongs two byte buffers between
  layers. The Rust layers take typed tensors, so each lives in its own scope
  and LLVM overlaps the stack slots of tensors that are never live together:
  the peak is still the stem's output plus the pooled tensor. The profile image
  keeps its layers in a separate frame; with them in the caller's frame the
  L031 ran out of its 8 KB of RAM.

### MLPerf Tiny keyword spotting (DS-CNN), translated from TFLite

C++ and TFLM figures are tinymind (C++)'s (`results/REPORT_mlperf.md`, `-O3`).

- The Rust model takes 31% fewer cycles than tinymind (C++)'s portable build, in
  6% less flash and 3% less RAM; tinymind (C++)'s SMLAD build and TFLM with
  CMSIS-NN are faster. The parallel-DSP flag does not change it. Its four

  from 32 input channels), as tinymind (C++)'s SMLAD kernel blocks them: each
  loaded input serves two filters and each weight two pixels. That took the
  model from 11,850,835 to 10,790,589 cycles (-9%) for 3,840 B more flash. With

  time. Per layer

  about 82 cycles per output: LLVM unrolls the 25x5 pixel loop and keeps the
  nine weights on the stack.

  translator of tinymind (C++) does, so the eight 25x5x64 layers ping-pong between two slots (16,000

- 31% fewer cycles than tinymind (C++)'s portable build, in 5% more flash and
  6% more RAM. Before the tuning below: 91,085,417 cycles, 101,076 B, 86,520 B
  (and the figures in these points, before the build settings were matched).
- Convolutions over several input channels (`conv2d_band` in
  `src/int8/conv.rs`) widen the `KH` input rows of each output row to `i16` as
  `x - zero_point`, and each filter's weights to `i16`, then add each window
  inside the input as `KH` dot products over contiguous `KW * C` values, in
  pairs: 91.1M to 68.4M cycles for the network (a 16-channel 3x3 layer then
  took 11.1M, 4.7 cycles per multiply-accumulate). Computing two filters at
  two pixels at a time was barely faster by default (68.0M), slower with the
  flag below (48.1M against 45.9M) and took 68 KB more flash: dropped.
- The three additions tabulate each input's rescaling for all 256 int8 values
  first: 185 cycles per element down to 22 (3.03M to 0.36M cycles for the
  first one).
- RAM: one planned byte arena (49,152 B, as tinymind (C++)'s), viewed as typed
  tensors through `as_chunks` and `first_chunk` (safe Rust, 1.88 or later in
  the generated module), with `split_at_mut` separating a layer's output from
  its inputs. Per-shape typed buffers needed 86,520 B. Most of the rest is
  the convolutions' 16-bit scratch (about 4.2 KB for the 64-channel layer) and
  the addition tables (2 KB).
- **SMLAD from stable Rust.** LLVM's Arm parallel-DSP pass turns two adjacent
  `i16` products added to one sum into `SMLAD`, on M4/M7/M33, with no
  intrinsics. It analyses at most 16 loads by default and gives up on the
  fully unrolled sums here; with `-C
  llvm-args=-arm-parallel-dsp-load-limit=512` it pairs them: 38,273,811 cycles,
  1.45 times tinymind (C++)'s +SMLAD build (which reads four int8 values per
  load with `SXTB16`, an intrinsic). The flag changes no other workload here.
  It is an LLVM internal option, so it is opt-in, not in this bench's config.
- The 16-bit path on the M0+ (no DSP): a 10x10x8 3x3 convolution measured
  675,064 cycles against 835,734 on the previous path (F411: 303,574 against
  451,012), with the same output.

### Decision trees, imported from scikit-learn

Cycles for one prediction (median of 33), first held-out sample.

| | F411 | L031 |
|---|---:|---:|
| Correct on 54 held-out samples (gbdt / forest), hash matches host | 53 / 53, yes | 53 / 53, yes |
| Gradient boosting, pool walk (pool in flash) | 8,828 (88 µs) | 17,780 (556 µs) |
| Gradient boosting, pool walk (pool copied to SRAM) | 7,751 | does not fit |
| Gradient boosting, nested `if`s | 1,680 (17 µs) | 2,627 (82 µs) |
| Random forest, pool walk / nested `if`s | 2,054 / 461 | 3,936 / 820 |
| First 36 trees (256 nodes, 3 KB): flash / SRAM copy | 3,793 / 3,345 | 6,586 / 6,170 |
| `quantize_features` (13 float divisions) | 637 | 11,292 |
| Flash (text), whole image | 56,388 B | 32,520 B (opt-level s) |

- **Where the model is.** The node pools are immutable `static`s, so
  cortex-m-rt's linker script puts them in `.rodata`, in flash (the
  image reports the pool's address, in the 0x0800_0000 flash range); `.data` is empty and
  nothing is copied to SRAM at start-up. The CPU reads the pool from flash, as
  it reads every instruction.
- **Flash versus SRAM.** Reading the pool from flash costs 13-14% on the F411
  (three wait states at 100 MHz, mostly hidden by the ART accelerator's prefetch
  and caches) and 7% on the L031 (one wait state at 32 MHz). The 7.5 KB pool
  would not fit beside the stack in the L031's 8 KB of SRAM anyway.
- **The form matters far more.** The nested-`if` form is 4.5-6.8 times faster
  than walking the pool: it compares against constants in the instruction
  stream and has no loop or index arithmetic. The pool is the smaller form.
- **Placement.** The same gradient-boosting walk measured 14,044 cycles on the
  L031 in an image that differed only in an extra test; as with the int8 MLP,
  the M0+ with one wait state is sensitive to code placement.

### Reading these

- Exactness holds on both cores: the integer arithmetic and every training step
  match the C++ and the host bit for bit.
- Against tinymind (C++)'s scalar C++ the Rust MLP takes 9% fewer cycles on
  the M4F and is 9-13% slower on the M0+ (the two figures are its two flash
  placements). It has no SMLAD path of its own:
  the Arm DSP intrinsics are nightly-only and `asm!` would break
  `forbid(unsafe_code)`. Only the multi-channel convolutions' 16-bit pairs reach
  SMLAD, through LLVM, with the opt-in option above.
- On the M0+ its RAM is about the C++'s (232 B against 224 B).

## Run

```bash
python3 -I bench/gen.py 360     # or 32 for the L031; run.sh does this
bench/run.sh                    # both boards; or: bench/run.sh f411
WORKLOADS="kws kws-profile" bench/run.sh f411 l031   # only some workloads
```

`run.sh` builds each image, records its size, flashes it with OpenOCD (ST-LINK
picked by serial number; override with `F411_STLINK` / `L031_STLINK`) and reads
the report from the ST-LINK's virtual COM port. Raw reports and images land in
`bench/results/` (not committed). CI builds every image, and runs them under
QEMU (below), not on the boards.

### Under QEMU

`scripts/qemu-bench.sh` runs the same images on QEMU's `mps2-an386` (Cortex-M4,
the F411's instruction set) and `microbit` (Cortex-M0, the same ARMv6-M
instructions as the L031's M0+), at opt-level 3, s and z, with the boards
`qemu-m4` and `qemu-m0` (`src/board.rs`: output and exit through semihosting).
A run fails on a panic, a missing end marker or any `*match=0`. QEMU does not
model cycles, so every timing reads 0: this checks correctness, on Arm code,
on every pull request (CI's `cpp-equivalence` job); timings need the boards.
`CORES=m4 OPTS=3 WORKLOADS="mlp kws" scripts/qemu-bench.sh` runs a subset.

The `sweeps` workload (`src/sweeps.rs`) runs every host test sweep on the
device: convolution and pooling, addition, composition (multiply, concat,
pad), softmax, the FFT (with tinymind (C++)'s twiddle tables from the
golden), the int8 LSTM and GRU cells, LSTM training, decision trees and
Q-learning, and the qformat oracle, from `tests/sweeps/`, which the host tests
include too. Each sweep writes its report into a sink that compares it line by
line, as it is written, with the committed golden from tinymind (C++)'s
program (no buffer: the goldens are in flash), and prints `<sweep>_match=1`,
or the first golden line that differs. The oracle checks itself against exact
arithmetic and must also run all of its default sample (105,792 checks on
16-bit storage, 134,485 on 32-bit).

Some of the host's report is not reproduced on the device:

- The addition, composition and softmax sweeps calibrate their layers with
  `int8::calibration`, which needs `std` (float rounding, `exp`). The golden
  prints every calibrated parameter, so on the device each calibrated layer
  takes the C++'s parameters from its golden line and must still produce the
  golden's output hash. The zero points and output range the sweep draws must
  agree with the line read, or the run fails (it is reading another trial's
  parameters).
- The int8 LSTM and GRU sweep's calibrated trials also need quantized weights,
  biases and lookup tables, which the golden prints only as hashes. On the
  device those trials run with zeroed parameters only to keep the generator in
  step, and only the direct-parameter trials (26 of 52 lines) are compared;
  the host compares all of them.
- The FFT sweep builds its twiddle tables with `int8::calibration` on the
  host; on the device it reads them from the golden's `twiddles ` lines, which
  the host also compares with what it built.
- The Q-learning sweep's maze line stays on the host (the maze driver uses
  `std`).

The image is large, and the LSTM sweep needs 73 KB of stack, so
`qemu-bench.sh` gives the microbit 2 MB of flash and 256 KB of RAM (`-global
nrf51-soc.flash-size`, `sram-size`; `memory-qemu-m0.x`); only the instruction
set is under test there. On the F411 it fits only at opt-level s (411 KB with
the FFT sweep, 2026-11-12; at 3 it exceeds the 512 KB): `OPT=s
WORKLOADS=sweeps bench/run.sh f411` matches on every sweep, in 355,889,556
cycles (3.6 s), with 73 KB of stack. It does not fit the L031. Planted defects that
fail it: the trees' `<=` as `<` (`tree_match=0`), a rounding Q-format
multiply (the oracle, the LSTM and Q-learning sweeps), a positive number
divided by zero giving max - 1 (only the oracle), addition subtracting a's
zero point from b, padding with 0, softmax dropping a logit exactly at
`diff_min`, and the GRU's `1 - z` off by one; each fails its own sweep only.

## Read the generated code

`scripts/emit-intermediates.sh arm` builds each board image with the flags
`run.sh` uses and keeps what the compiler produced on the way, under
`target/intermediates/arm/<board>/`: per workload the MIR (`.mir`), the
optimised LLVM IR (`.ll`), the assembly (`.s`) and a disassembly of the linked
image (`.lst`, with final addresses and loop alignment). No board is needed.
`BOARDS`, `WORKLOADS` and `OPT` select what is built, as for `run.sh`;
`scripts/emit-intermediates.sh host` does the same for the programs in
`examples/` on this machine. The script's header has the details.
