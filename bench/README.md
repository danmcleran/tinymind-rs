# On-board checks

Functionality and performance of the `tinymind` crate on two boards, mirroring
tinymind (C++)'s [framework comparison](https://github.com/danmcleran/tinymind/tree/master/benchmarks/framework_comparison_f411):
same boards, clocks, flash wait states, timing method, model weights and test
samples, so the numbers sit next to the tinymind (C++) ones.

| Board | Core | Clock | Timing |
|---|---|---|---|
| NUCLEO-F411RE | Cortex-M4F | 100 MHz, 3 wait states, ART on | DWT cycle counter |
| NUCLEO-L031K6 | Cortex-M0+ (no DSP, no hardware divide) | 32 MHz, 1 wait state, prefetch on | SysTick with wrap interrupt (no DWT on M0+) |

`src/board.rs` is a register-level port of tinymind (C++)'s `board/board.cpp` and
`board/board_l031k6.cpp`. Cycle counts are the median of 33 warm runs.

## Workloads

- **`mlp`**: tinymind (C++)'s int8 digits MLP (64-32-16-10, per-channel requantizers,
  ReLU fused into the requantizer) on `QDensePerChannel`, generated by `gen.py`
  from tinymind (C++)'s benchmark headers: the same int8 weights, requantizers and test
  samples (360 on the F411, the first 32 on the L031, as tinymind (C++) uses). The
  output hash over every sample must equal tinymind (C++)'s expected hash, which
  tinymind (C++) and TFLM both produce on these boards.
- **`xor-q16`, `xor-q8`**: tinymind (C++)'s xor example trained on the board, 20,000
  steps in Q16.16 and in Q8.8. The device hashes the exact bytes of the
  `nn_fixed_xor.txt` the example writes (every weight after every step) and
  compares with the golden hash in `tests/xor_golden.rs`.
- **`anomaly`**: the anomaly-detection demo (`examples/common/anomaly_demo.rs`,
  shared with `examples/anomaly.rs`): an 8-4-8 Q16.16 autoencoder trains on 3,000
  synthetic normal windows on the device, sets its threshold and screens 512 test
  windows. The report must equal the host's, and its hash (every trained weight
  and every score) must equal `EXPECT_HASH` in `src/anomaly.rs`, which the host
  run and `tests/anomaly_golden.rs` pin. No C++ counterpart.
- **`trees`**: the two imported scikit-learn models of the `imported_trees`
  example (gradient boosting, 90 trees on int8 inputs; random forest, 15
  voting trees on int16) classify the 54 held-out UCI Wine samples; the hash of
  every raw output and class must equal the host's (`EXPECT_HASH` in
  `src/trees.rs`). Both forms are timed, and the pool walk is timed from flash
  and from a copy in SRAM. The L031 image is built at `opt-level = "s"` to fit.
- **`kws`**: tinymind (C++)'s KWS-shaped int8 CNN from its framework comparison
  (20x20x1 input, conv 3x3x8 and pointwise layers with per-channel
  requantizers, 2x2 max pool, 3x3 depthwise, global average pool, a 16-10 dense
  head; random weights and inputs), generated by `gen.py` from tinymind (C++)'s
  benchmark headers. The output hash over its 8 test inputs must equal
  tinymind (C++)'s, which TFLM also produces. **`kws-profile`**: the same with
  per-layer timing.
- **`mlperf-kws`** (F411 only): the MLPerf Tiny keyword-spotting reference model
  (DS-CNN, 49x10 MFCC input, 12 classes), translated from its `.tflite` by
  `tools/import_tflite`. Generate it first with `python3 -I
  tools/import_tflite/mlperf.py kws --out bench/src/gen/mlperf_kws.rs --data
  bench/src/gen/mlperf_kws_data.rs` (a Python with `tflite`; the model is
  downloaded, Apache-2.0, not committed), then `WORKLOADS="mlperf-kws"
  bench/run.sh f411`. Its output hash over 8 seeded random inputs must equal
  tinymind (C++)'s, which TFLite's reference kernels also produce.
- **`mlperf-ic`** (F411 only): the MLPerf Tiny image-classification reference
  model (ResNet-8, 32x32x3 input, 10 classes, three residual blocks), the same
  way: `mlperf.py ic --out bench/src/gen/mlperf_ic.rs --data
  bench/src/gen/mlperf_ic_data.rs`, then `WORKLOADS="mlperf-ic" bench/run.sh
  f411`.
- **baseline** (no workload feature): the MLP harness with a do-nothing network,
  for size and stack deltas. **`profile`**: the MLP with per-layer timing.

## Results (2026-11-07)

Rust 1.99.1, `opt-level = 3`, LTO, one codegen unit. C++ figures are tinymind (C++)'s
own (`docs/benchmarks.md`, gcc 13.2.1 `-O3`), measured on these same boards.

### KWS-shaped CNN (int8 convolutions)

C++ figures are tinymind (C++)'s (`benchmarks/framework_comparison_f411/README.md`).
Code + weights = image - baseline image - test inputs (3,200 B); RAM = static
data plus peak stack, each above the baseline's.

| | F411 (100 MHz) | L031 (32 MHz) |
|---|---:|---:|
| **tinymind-rs**, cycles | **189,557** (1.90 ms) | **651,332** (20.4 ms) |
| tinymind (C++) scalar, `-O3` | 254,900 | 746,112 |
| tinymind (C++) +SMLAD, `-O3` | 181,568 | – (no SMLAD on the M0+) |
| TFLM int8 (CMSIS-NN), `-O3` | 576,368 | does not fit in 32 KB |
| **tinymind-rs**, code + weights / RAM | **8,712 B / 4,668 B** | **9,228 B / 4,864 B** |
| tinymind (C++) scalar `-O3`, flash / RAM | 6,848 B / 5,332 B | 8,452 B / 5,488 B |
| tinymind-rs at `opt-level = "s"`, cycles / code + weights | 664,196 / 3,632 B | 1,230,230 / 3,724 B |

Per layer (cycles, each layer timed separately; C++ scalar `-O3` in brackets):

| Layer | F411 | L031 |
|---|---:|---:|
| conv 3x3, 8 filters | 112,047 (173,164) | 414,052 (516,155) |
| max pool 2x2 | 10,708 (10,156) | 20,192 (24,921) |
| depthwise 3x3 | 22,732 (21,054) | 69,218 (73,079) |
| pointwise 8 -> 16 | 41,028 (44,258) | 137,126 (137,483) |
| global average pool | 2,504 (2,282) | 4,704 (5,756) |
| dense 16 -> 10 | 1,609 (1,281) | 3,347 (2,830) |

- **Faster than the portable C++.** The Rust model takes 26% fewer cycles than
  tinymind (C++)'s portable build on the M4F and 13% fewer on the M0+, and is
  4% behind its SMLAD build on the M4F, without SIMD. It uses less RAM, and
  27% (M4F) and 9% (M0+) more flash than the C++ at `-O3`: LLVM unrolls the
  layers' loops fully at `opt-level = 3`. At `opt-level = "s"` the network's
  code and weights take 3.6-3.7 KB, but it runs 1.9-3.5x slower.
- **Where it comes from.** The stem convolution (one input channel) reads each
  window once for all filters and is 20-35% faster than the C++'s gathered
  patches. Depthwise and pointwise run as the C++ does: filter by filter, with
  the zero point folded into the bias, the weights held across the pixels and
  the requantizer prepared once per filter (tinymind (C++)'s `FastRequantizer`,
  extended to the ranges of a fused ReLU and proved equal to `apply` by Kani).
  A depthwise window that lies inside the input reads it as slices without
  per-tap checks. That took depthwise from 46,049 to 22,732 cycles and
  pointwise from 78,614 to 41,028 on the M4F.
- **Measured, not assumed.** Running the stem filter by filter as well made
  it 20% slower (135,172 cycles), so it keeps its window-once loop. One pixel
  loop branching on the requantizer form per output, instead of one loop per
  form, saved 0.5 KB and cost depthwise 27%. Requantizers without a prepared
  form (a scale ratio of 0.25 or more) run a cold out-of-line loop: on this
  model they would cost depthwise 31% and pointwise 36%.
- **No buffer reuse needed.** The C++ ping-pongs two byte buffers between
  layers. The Rust layers take typed tensors, so each lives in its own scope
  and LLVM overlaps the stack slots of tensors that are never live together:
  the peak is still the stem's output plus the pooled tensor. The profile image
  keeps its layers in a separate frame; with them in the caller's frame the
  L031 ran out of its 8 KB of RAM.

### MLPerf Tiny keyword spotting (DS-CNN), translated from TFLite

C++ and TFLM figures are tinymind (C++)'s (`results/REPORT_mlperf.md`, `-O3`).
These are not MLPerf results: no accuracy run, no energy measurement, not
verified by MLCommons. Code + weights = image - baseline image - test inputs
(3,920 B); RAM = static data plus peak stack above the baseline's (TFLM's
includes its tensor arena).

| F411, 100 MHz | Cycles | Time | Code + weights | RAM |
|---|---:|---:|---:|---:|
| **tinymind-rs** | **16,115,226** | **161.2 ms** | **45,732 B** | **16,336 B** |
| tinymind (C++), scalar | 15,736,026 | 157.4 ms | 52,748 B | 17,264 B |
| tinymind (C++), +SMLAD | 8,193,064 | 81.9 ms | 53,156 B | 17,248 B |
| TFLM int8 (CMSIS-NN) | 9,583,099 | 95.8 ms | 148,864 B | 24,432 B |
| TFLM int8 (reference kernels) | 67,484,238 | 674.8 ms | 101,944 B | 23,828 B |

- The Rust model takes 2.4% more cycles than tinymind (C++)'s portable build, in
  13% less flash and 5% less RAM; tinymind (C++)'s SMLAD build and TFLM with
  CMSIS-NN are faster, as neither SIMD path is available to the Rust port.
- RAM: the translator gives each feature-map shape as many buffers as are live
  at once, so the eight 25x5x64 layers ping-pong between two (16,000 B), as
  tinymind (C++)'s planned arena does. A first version nested each layer in its
  own block instead and peaked at three tensors (24,512 B): the value each block
  returned took a slot of its own.
- Re-measured 2026-11-09 (16,125,065 cycles and 45,776 B before; the bench crate
  changed, the module did not). A library change that moved the code after it
  by 10 bytes, and changed nothing else, measured 17,882,704 cycles: built with
  `-C llvm-args=-align-loops=16`, both versions take 16,197,424-16,197,426 cycles. F411 timings
  depend on where hot loops fall against the flash lines, so differences of a
  few percent between builds are not necessarily the code.

### MLPerf Tiny image classification (ResNet-8), translated from TFLite

Same method and caveats. Test inputs are 24,576 B.

| F411, 100 MHz | Cycles | Time | Code + weights | RAM |
|---|---:|---:|---:|---:|
| **tinymind-rs** | **91,096,190** | **911.0 ms** | **100,220 B** | **86,520 B** |
| tinymind (C++), scalar | 85,467,754 | 854.7 ms | 120,836 B | 54,380 B |
| tinymind (C++), +SMLAD | 26,753,191 | 267.5 ms | 108,324 B | 54,424 B |
| TFLM int8 (CMSIS-NN) | 37,372,049 | 373.7 ms | 191,212 B | 56,608 B |
| TFLM int8 (reference kernels) | 191,555,451 | 1,915.6 ms | 155,412 B | 55,396 B |

- 6.6% more cycles than tinymind (C++)'s portable build, in 17% less flash. The
  3x3 convolutions over 16 to 64 channels (most of the work) are not tuned on
  the board yet.
- RAM is 59% higher: the module keeps three buffers of each of the three
  feature-map shapes (3 x 16,384 + 3 x 8,192 + 3 x 4,096 B), while the planned
  byte arena of tinymind (C++) reuses the same 49,152 B across shapes. Typed
  arrays of different shapes cannot share storage without `unsafe`.

### Decision trees, imported from scikit-learn

Cycles for one prediction (median of 33), first held-out sample.

| | F411 | L031 |
|---|---:|---:|
| Correct on 54 held-out samples (gbdt / forest), hash matches host | 53 / 53, yes | 53 / 53, yes |
| Gradient boosting, pool walk (pool in flash) | 9,095 (91 µs) | 17,780 (556 µs) |
| Gradient boosting, pool walk (pool copied to SRAM) | 8,027 | does not fit |
| Gradient boosting, nested `if`s | 1,841 (18 µs) | 2,627 (82 µs) |
| Random forest, pool walk / nested `if`s | 2,024 / 462 | 3,936 / 820 |
| First 36 trees (256 nodes, 3 KB): flash / SRAM copy | 3,480 / 3,129 | 6,586 / 6,170 |
| `quantize_features` (13 float divisions) | 608 | 11,292 |
| Flash (text), whole image | 48,972 B | 32,520 B (opt-level s) |

- **Where the model is.** The node pools are immutable `static`s, so
  cortex-m-rt's linker script puts them in `.rodata`, in flash (the
  image reports the pool's address, in the 0x0800_0000 flash range); `.data` is empty and
  nothing is copied to SRAM at start-up. The CPU reads the pool from flash, as
  it reads every instruction.
- **Flash versus SRAM.** Reading the pool from flash costs 11-13% on the F411
  (three wait states at 100 MHz, mostly hidden by the ART accelerator's prefetch
  and caches) and 7% on the L031 (one wait state at 32 MHz). The 7.5 KB pool
  would not fit beside the stack in the L031's 8 KB of SRAM anyway.
- **The form matters far more.** The nested-`if` form is 4.4-6.8 times faster
  than walking the pool: it compares against constants in the instruction
  stream and has no loop or index arithmetic. The pool is the smaller form.
- **Placement.** The same gradient-boosting walk measured 14,044 cycles on the
  L031 in an image that differed only in an extra test; as with the int8 MLP,
  the M0+ with one wait state is sensitive to code placement.

### Reading these

- Exactness holds on both cores: the integer arithmetic and every training step
  match the C++ and the host bit for bit.
- Against tinymind (C++)'s scalar C++ the Rust port is 4% slower on the M4F and 7-18%
  slower on the M0+, at about the same size. It has no SMLAD path: the Arm DSP
  intrinsics are nightly-only and `asm!` would break `forbid(unsafe_code)`.
- On the M0+ the stack use is higher than the C++'s (472 B against 200 B).

## Run

```bash
python3 -I bench/gen.py 360     # or 32 for the L031; run.sh does this
bench/run.sh                    # both boards; or: bench/run.sh f411
WORKLOADS="kws kws-profile" bench/run.sh f411 l031   # only some workloads
```

`run.sh` builds each image, records its size, flashes it with OpenOCD (ST-LINK
picked by serial number; override with `F411_STLINK` / `L031_STLINK`) and reads
the report from the ST-LINK's virtual COM port. Raw reports and images land in
`bench/results/` (not committed). CI builds every image but does not run them.
